# ML Workspace

Everything the app's on-device LLM and rule data are built from: data, the
Python package that builds and evaluates them, the files the app ships, and
the records of how well they do. The Android app reads only `runtime/`; the
rest stays out of the APK.

The model is Qwen3-1.7B fine-tuned with LoRA and run with llama.cpp. It reads
what a landing page shows and gives the pipeline's final verdict. An earlier
URL-feature model was removed; why, and its version history, are in the
[Technical Report](../docs/technical-report.md#7-earlier-approach-url-model).

## 1. Layout

| Path | Content |
| :-- | :-- |
| `guadian_ml/` | Python package: `llm/`, `resources/` (allowlist, blocklist, and brand-data builders), `shared/`, `paths.py` |
| `tests/` | unit tests, one directory per subpackage |
| `data/` | datasets: `raw/` (original GUADIAN gold set), `url/` (labeled URLs for the rule report), `llm/` (git-ignored) |
| `fixtures/` | small synthetic cases the Kotlin tests read to match the Python reference |
| `runtime/` | files the app loads: brand tables, allowlist, blocklist filter |
| `reports/` | generated evaluation records and reports: `llm/`, `pipeline/` |
| `notebooks/` | the generated Colab training notebook |
| `docs/` | the LLM's dataset document and model card |

`paths.py` names every one of these locations, so no module builds paths of its
own.

## 2. Setup

The package needs Python 3.11 or later. From the repository root:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e "ml[llm]"      # data collection, labeling, notebook, evaluation
python -m unittest discover -s ml/tests -t ml
```

`ml[test]` installs only what the tests need, and is what CI uses. Every
dependency is pinned in `pyproject.toml`.

## 3. On-device LLM

The model reads a short prompt built from what the phone can observe on a page
(address, title, visible text, form fields, APK links, redirects) and answers
with one JSON line: risk, type, and, for `HIGH`, the prompt line that proves
it. How the data was collected, labeled, and split is in
[LLM Dataset](docs/llm/dataset.md); intended use, results, and limits are in
the [LLM Model Card](docs/llm/model-card.md).

The prompt format and the reply reading are a contract between training and
the app. `guadian_ml/llm/contract/` is the reference, `core/llm` ports it to
Kotlin, and `python -m guadian_ml.llm.contract.fixtures` writes the cases in
`fixtures/llm/` that the Kotlin parity tests replay.

Training runs in Colab from `notebooks/train_llm.ipynb`, generated by
`python -m guadian_ml.llm.training.notebook`. A trained GGUF model is scored
with `python -m guadian_ml.llm.evaluation.gguf MODEL.gguf --name NAME`, which
writes `reports/llm/NAME_test.json`. With several quantizations of one run
scored, `python -m guadian_ml.llm.evaluation.agreement RUN` records how often
they give the same risk, and `python -m guadian_ml.llm.evaluation.report`
turns all the records into the
[LLM Evaluation Report](reports/llm/evaluation-report.md).

## 4. Runtime Files

| File | Built by |
| :-- | :-- |
| `official_domains.txt` | `python -m guadian_ml.resources.official_domains --tranco top-1m.csv` |
| `blocklist.bloom`, `blocklist.meta.json` | `python -m guadian_ml.resources.blocklist` |
| `llm_brands.json` | `python -m guadian_ml.resources.llm_brands` |
| `brand_domains.tsv` | edited by hand |
| `public_suffix_list.dat` | Mozilla Public Suffix List |

Each `core` module adds the `runtime/` files it reads to its resources, so
Python and Kotlin read the same files with no export step. The
[Local Resolution Report](reports/pipeline/local-resolution-report.md), which
measures the rules and local knowledge on `data/url/sample_urls.csv`, is
written by `./gradlew :core:judge:writeLocalResolutionReport`. Sources and
licenses of every file are in [Provenance](../docs/provenance.md).
